| D23 | Decided (replaced 18 Nov 2026) | **Signed intent messages, not co-signed transactions.** This replaces the earlier durable-nonce decision. Per the Solana research, durable nonces are being deprecated, are associated with the Drift exploit, and apps should avoid asking users to sign them. Blockhash lifetime is now about 30 s, and wallet `signTransactions` is deprecated in Mobile Wallet Adapter. Every action needing approval from people on different devices works by signed messages: handovers, loading acceptances and joint redemption. (1) Each party signs a **human-readable, domain-separated intent message** with their wallet's message signing. The message states program instance, action, lot/batch, quantity, from/to organisations, manifest digest, expected sequence or revision, and an expiry **slot**. (2) The backend sponsor (D24) builds an ordinary recent-blockhash transaction carrying both signed messages and submits it. (3) The Thetis program verifies each signature, the exact message bytes, the registered authority's key, the expiry slot and the expected sequence, then applies the change atomically. Replay protection is the program's own per-batch handover sequence and per-intent revisions; a used or stale message fails. Cancellation needs no on-chain action before submission: an unsubmitted message expires at its slot, and any later state change invalidates its expected revision. The verification route (in-house, Anza Programmatic Signer or Blueshift Vector) is D32. Required negative tests, in addition to A10–A11: swapped signer, message for another batch or instance, altered quantity or manifest, reused message after success, expired slot, a verification instruction pointing at other data, and an attempt to substitute the instructions sysvar. ## Phase-0 notes from the Solana research, 18 November 2026

Source: the reports and notes in `/home/kirito/Documents/projects/personal/Solana/` (compiled 15–16 November 2026), plus primary pages for D32 checked on 18 November 2026. Versions are starting points; pin what is actually tested (phase-0 step 3).

**Toolchain and clients**

- **Programs:** Anchor 1.2.x (stable since April 2026; TypeScript package `@anchor-lang/core`, not the frozen `@coral-xyz/anchor`). Use the platform tools Anchor recommends (Solana 3.1.10), not the newest validator. Anchor 1.x rejects duplicate mutable accounts by default and allows one `#[error_code]` per program.
- **Tests:** LiteSVM for unit and scenario tests, Mollusk for single-instruction compute benchmarks, Surfpool as the local validator. `solana-bankrun` is deprecated. Trident fuzzing guides pin Anchor 0.32.1, so check Anchor 1.x support before adopting it.
- **Clients:** `@solana/kit` 8.x with Codama-generated clients from the Anchor IDL. Do not start on `@solana/web3.js` 1.x. A plain install now resolves to v3, which uses bigint, `Uint8Array` and async signing.
- **Web wallets:** `@solana/wallet-adapter` 3.x is ESM-only and needs React ≥19.3.1, which constrains the Next.js version. Phantom Portal accepts no new applications, so the embedded-wallet choice is among Privy, Dynamic, Turnkey and Para. Kit's `walletIdentity` plugin supports the D24 sponsor pattern.
- **Mobile:** scaffold with `npx solana-mobile@latest create` (template `expo-kit-minimal`: Expo ~58, React Native 0.88, React 19.3, Kit ^8.4). Require the MWA JS packages at 3.0.2, `wallet-adapter-mobile` ≥3.0.1 and `wallet-standard-mobile` ≥0.7.1; earlier versions silently dropped commitment options or hung. Expo Go cannot run MWA, so use a dev build. Use the Mock MWA Wallet on an emulator, which needs a PIN lock screen, for most testing. Use the Seeker for Seed Vault Wallet and Seeker Connect behaviour. Host `assetlinks.json` (Digital Asset Links) on the web domain so wallets can verify the app. MWA is Android-only, which suits the field roles.
- **Seeker Connect:** a `session-closed` error does not mean failure, so check the chain before retrying. The design's `outcome unknown` state applies.

**Network behaviour after the 2026 upgrades**

- Blockhash lifetime is about 30 s (200 ms slots), so sponsor-built transactions are built immediately before sending. Send with `maxRetries: 0` and rebroadcast until `lastValidBlockHeight`. Re-sign only after expiry.
- `confirmed` and `finalized` now describe the same state. Request `finalized` everywhere, including the indexer, to avoid Alpenglow's multiple candidate blocks per slot. Use `confirmationStatus` and `signatureSubscribe`, not the `confirmations` count.
- `Clock.unix_timestamp` is set by the leader. Use slot-based expiries for D23 messages. Accept small timestamp drift for interest accrual on devnet, and bound it before production.
- v1 transactions allow up to 4 KB and 64 inline accounts, with no lookup tables. Two signed messages plus their verification fit; size each instruction in phase 0.
- Rent fell sharply in 2026, so per-batch accounts and permanent tombstones are cheap.

**Tokens**

- D25 receipts use Token-2022 without permanent delegate or transfer hooks; the research flags both as risk surfaces. D31's Circle devnet USDC is a classic SPL Token mint, so the program uses Anchor's token-interface types and `transfer_checked`, and validates the token-program ID per mint.
- There are no on-chain price oracles (D12): Switchboard shut down in September 2026 and Pyth became paid.
- Optional: the Solana Attestation Service could carry custodian accreditation credentials. This is not adopted; consider it in phase 1.

**Security and repository signals**

- Ship `security.txt` in the program and a reproducible (verified) build from the public repository, because stage 2 inspects code.
- The devnet single admin is disclosed (DESIGN §3). Any live deployment uses a Squads vault as upgrade authority, with a timelock on admin actions. The Drift loss came from social engineering of signers, not a code bug.
- Anchor's typed accounts do not cover `remaining_accounts`, `UncheckedAccount`, `init_if_needed` or arithmetic. D23's instructions-sysvar verification is custom code: test it adversarially (D23 negative tests).

## Concrete questions for the first design review

1. Which organisation operates the first custodian and who signs on each shift? Obtain a delegation and recovery policy.
2. Does the port maintain segregated lots or balances of a grade? That decides whether phase 6 is needed for the intended physical scenario.
3. What loan balance and release rule does the lender recognise? Choose all receipts swept to debt as the initial rule, as in the original project, unless the facility explicitly requires otherwise.
4. Which transport document is available at loading and which parties accept the transition of collateral control? Pending-document and actual-onboard events may occur at different times; use a blocked workflow until the required accepted evidence exists.
5. Who pays for the pilot, who supplies capital, and which observed cost is expected to fall? Do not assume lower interest is the benefit.

The design can be implemented with synthetic participants and fixtures before these commercial answers exist. It cannot be represented as a live finance service or a legally effective security system on that basis.
